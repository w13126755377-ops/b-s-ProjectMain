## 一、实验概述

### 1.1 实验目的

独立开发一个可运行的企业审批 Web 应用，覆盖采购审批、差旅申请、报销审批，以及系统管理员自主定义的其他审批流程；通过多个部门、不同权限的用户，演示申请提交、逐级审批、结果查询和操作留痕的完整过程。系统须使用数据库持久化业务数据，提供可复现的 Docker 部署，并实现持久化站内通知等基础功能与若干增强功能（委托、超时催办、跨申请重复票据预警、Web Push、移动端响应式适配等）。

## 二、系统实现总结

### 2.1 总体架构

前后端分离的 B/S 三层架构：

```
浏览器（Vue3 SPA，移动端响应式）
      │  HTTP / SSE
      ▼
nginx（静态托管 + /api 反代）
      │
      ▼
Express 后端（路由 → 服务 → MySQL）
  ├─ auth / users / departments     认证与资料
  ├─ applications / tasks           申请与审批（状态机引擎）
  ├─ attachments                    附件（格式/权限/MD5 去重）
  ├─ notifications / push           通知（站内 + SSE + Web Push）
  ├─ templates                      自定义流程模板
  ├─ delegations                    审批委托
  ├─ stats                          查询统计
  └─ admin                          管理后台（审计留痕）
      │
      ▼
MySQL 8.0（结构 01_schema.sql + 种子 02_seed.sql）
```

### 2.2 核心机制

1. **角色与权限（服务端强制）**：EMPLOYEE / DEPT_HEAD / FINANCE / COMPANY_HEAD / ADMIN 五角色（用户-角色多对多）；权限检查在列表、详情、审批、附件预览下载等每个接口的 SQL 层与业务层强制执行，不依赖前端隐藏按钮；管理员权限 ≠ 审批权限，业务正文/票据须在审批链内另行授权。
2. **状态机审批引擎**：DRAFT → IN_APPROVAL → APPROVED / REJECTED / WITHDRAWN；提交时全量保存审批链快照（人员、阈值、规则口径），后续配置变化不改写存量实例；顺序审批、驳回必填理由、不可自审、双击/双浏览器幂等、撤回与审批并发仅一方生效。
3. **三类内置流程 + 自定义流程**：采购（≥2 明细、≥2 报价或单一来源、非最低价须说明）、差旅（起止校验、系统按"自然日-时长折算"计算天数、可关联报销）、报销（≥3 明细 5 类费用、整数"分"重算合计、每条明细 ≥1 票据或无票原因、跨单重复预警）；管理员可在线创建/编辑/发布/停用自定义模板（字段 text/textarea/number/amount/date/radio/attachment，≥2 可排序节点，发布前校验字段标识唯一、条件引用有效等）。
4. **附件**：仅 JPEG/PNG/PDF、单文件 ≤10MB、数量/总大小上限；biz_type 与申请类型一致性校验防票据伪装；MD5 + 票据号跨单重复检测；仅草稿可上传/删除。
5. **通知**：新待办/通过/驳回/撤回持久化站内通知，未读数、标记已读、点击跳转、幂等去重；SSE 实时推送 + Web Push 后台触达 + 轮询兜底。
6. **统计**：个人/部门/企业口径，按提交时间统计，已通过金额不含草稿/驳回/撤回；部门统计按角色与 `stats_grants` 明确授权定范围；ECharts 图表展示。
7. **安全**：bcrypt 密码哈希、JWT（7 天）、参数 zod 校验、SQL 参数化、错误统一封装（HTTP 状态码 = 业务码）、审计日志（角色授予/模板/配置/统计授权变更留痕）。

> 详细设计见《设计文档》17 章：数据库 ER 图与 20+ 张表、权限矩阵、审批引擎、接口清单、部署编排。

## 三、测试报告

### 3.1 测试方法

编写端到端（E2E）自动化验收脚本 `backend/scripts/e2e.mjs`，直接以真实 HTTP 请求驱动后端，验证完整业务链路与服务端权限/状态机行为。脚本断言覆盖注册登录、三类流程全链路、状态机、并发幂等、委托自审、自定义模板、附件规则、通知、统计口径、管理后台、模板版本演进与超时催办。

**运行方式**（需先 `docker compose up -d` 启动系统，或本地启动后端）：

```bash
node backend/scripts/e2e.mjs            # 常规场景（154 项断言）
E2E_SLOW=1 node backend/scripts/e2e.mjs # 追加超时催办慢场景（+200s，共 156 项）
```

> 统计类断言核对"绝对金额/数量"，每次完整运行前需重置数据：`docker compose down -v && docker compose up -d`。

### 3.3 过程中发现并修复的关键缺陷

| 缺陷 | 现象 | 修复 |
| --- | --- | --- |
| 附件格式校验返回 500 | TXT/GIF 上传被 multer 拒绝后落到通用 500 | fileFilter 抛 `AppError(400)` |
| 部门统计范围错误 | 部门负责人 `amountByDept` 仍返回全部门 | `deptFilter` 从 JOIN 条件移到 WHERE |
| 配置接口未拦截未知键 | 白名单外键被 zod strip 后静默成功 | zod `.strict()` 返回 400 |
| 报销草稿被误拒 | 校验要求每条明细至少 1 票据，草稿无法先建后传票 | 完整性校验移到提交时执行 |
| 自审场景委托失效 | 自审检查先于委托解析触发 | 自审检查移到委托解析之后 |
| 统计口径部门 ID 误标 | 断言把"市场部"写成 dept 3（实为 dept 2） | 修正为 dept 2 |

> 其余历史修复（部门统计趋势子查询别名、评审发现的 2 个 critical 等）见 git log。

## 五、开发过程与体会

开发按"设计文档 → 后端 → 前端 → Docker → 端到端验收"推进（见设计文档附录《开发里程碑》），git 全程管理，共 6 次提交。主要体会：

1. **服务端才是权限边界**：前端隐藏按钮只是体验优化，所有列表/详情/审批/附件接口都在 SQL 与业务层强制校验数据范围，避免"改请求字段提权"。
2. **状态机与并发要先想清楚**：快照隔离让"配置变更不影响存量实例"得以成立；双击幂等、撤回/审批并发"单赢"通过唯一约束 + 事务 + 状态重校验实现，E2E 的并发断言（`Promise.all`）起了决定性作用。
3. **金额用整数"分"**：服务端重算合计 + 整数分，彻底规避浮点误差决定审批路径的风险。
4. **可复现部署与可复现验收同等重要**：`down -v && up -d` 一键重置种子数据，让"绝对金额/数量"类断言可重复验证；E2E 脚本成为每次改动后的回归基线。
